## TL;DR
> A full, real walkthrough of applying GitHub Spec Kit's spec-driven development workflow (`constitution` → `specify` → `clarify` → `plan` → `tasks` → `analyze` → `implement`) to add a new "reading list" feature to an existing, decade-old Hugo static blog — instead of starting a project from scratch. The presenter bootstraps Spec Kit directly into the existing repo with `specify --here`, keeps every command scoped to the site's real constraints (no frameworks, no tests, Hugo templates only), and shows how clarify/analyze catch gaps and inconsistencies before code gets written, finishing with the learnings fed back into the spec file itself.

**Watch this if:** you already have an existing codebase and want to see exactly how to retrofit GitHub Spec Kit's spec-driven process onto it instead of only using it for greenfield projects.

## Key Takeaways
- Bootstrap Spec Kit directly into an existing project with `specify --here` instead of creating a new project folder — it warns about overwriting files but adds a `.specify` folder (memory/scripts/templates) and slash commands (`constitution`, `specify`, `clarify`, `plan`, `tasks`, `analyze`, `implement`) without touching existing site files.
- The `constitution` command generates project-wide constraints; always review and edit it manually — the presenter removed AI-generated claims (like "all content is human-written") that had nothing to do with the actual code/infrastructure work being automated, keeping only real constraints (static site only, Hugo as sole build tool, theme-based styling, zero external dependencies).
- The `specify` command needs concrete, specific requirements grounded in real knowledge of the existing system (e.g. "use the existing TOML config for footer links" instead of letting the model guess) — the more you let an LLM guess, the more likely it derails.
- `clarify` surfaces genuine blind spots the presenter missed in the first pass: book ordering (most-recently-finished first), pagination size (20 per page), star-rating display format, how to handle in-progress books ("currently reading" with special styling), and how to handle invalid/missing TOML data (skip silently).
- `plan` translates the spec into a technical approach; the presenter explicitly stripped out test-related scaffolding the template generated by default, since this blog has never used automated tests and didn't need them for a low-stakes hobby project.
- `analyze` cross-checks spec/plan/tasks for inconsistencies before implementation — it caught a data-directory-location mismatch (spec said "config data directory," Hugo convention says a dedicated `data` directory) and flagged missing truncation/asset-build details, which were fixed and pushed back into the spec.
- `implement` (run with Claude Sonnet 4, later iterated with GPT-5) generated the actual Hugo template, partials, and CSS; the first pass built the correct data binding but not the intended visual grid, requiring a follow-up iteration round with model-switching to land on the right design.
- After the feature was styled correctly, the presenter explicitly asked the agent to encode the session's design learnings (not implementation details) back into `spec.md` as new functional requirements — so a future full rebuild (e.g. migrating off Hugo) could reuse the same spec and skip re-litigating the same design decisions.

## ✅ Action Items
- If retrofitting Spec Kit onto an existing project, run `specify --here` instead of creating a new project directory, and manually review/prune the generated constitution to remove irrelevant AI-invented constraints.
- Be explicit in `/specify` about existing conventions (config formats, file locations, styling rules) instead of letting the model guess — it reduces derailment.
- Always run `/clarify` before `/plan` to surface genuinely underspecified decisions (ordering, pagination, edge-case data handling) you didn't think to write down.
- Strip unnecessary scaffolding (like test generation) from `/plan` output when it doesn't match your project's real needs and scale.
- Run `/analyze` before `/implement` to catch spec/plan/task inconsistencies (e.g. file-location mismatches) early.
- After implementing and iterating on a feature, explicitly ask the agent to fold the session's design learnings back into `spec.md` so future rebuilds can reuse the same spec.
