## TL;DR
> The AI Automators breaks down Anthropic's new engineering blog post on harness design for long-running agents. The core problem: agents that grade their own work approve it almost every time, even when it's mediocre. Anthropic's fix borrows from GAN architecture — a separate generator and evaluator agent whose tension drives quality up — demonstrated with a 6-hour autonomous 2D game maker and a ~4-hour, $125 in-browser DAW, both built on the Claude Agent SDK.

**Watch this if:** you're building any multi-step autonomous agent system (coding or not) and need it to actually finish, and finish well, without a human checking every step.

## Key Takeaways
- A harness is the orchestration layer around a model — prompts, tools, feedback loops, constraints, validation — that keeps a raw model "in a direction," much like a harness controls a horse's raw power.
- Anthropic identified two failure modes in long-running agents: "context anxiety" (as context fills up, models rush and declare things done prematurely — Sonnet 4.5 showed this even with context compaction) and poor self-evaluation (agents that grade their own work approve it almost every time, even when a human would call it mediocre).
- Opus 4.6, with its 1M-token context window, showed far less context anxiety than Sonnet 4.5/Opus 4.5, letting Anthropic drop explicit context-reset handoffs in favor of built-in context compaction — though the presenter is skeptical this fully eliminates the need for resets going forward.
- Anthropic's solution is adversarial evaluation, GAN-style: a generator agent creates the work, a dedicated evaluator agent (whose system prompt is built to be skeptical) grades it, and the tension between them drives quality up — proven more effective than asking one agent to critique its own output.
- Getting the evaluator to actually work took three refinements: making subjective quality gradable via explicit criteria (design quality, originality/anti-AI-slop, craft, functionality), weighting those criteria toward the model's known weaknesses, and letting the evaluator interact with the actual output (via the Playwright MCP) rather than just reading code.
- Case study 1 (front-end design, single generator/evaluator loop): 5-15 rounds of feedback on a Dutch art museum website produced a genuinely novel 3D checkered-floor design no single pass had produced.
- Case study 2 (2D retro game maker, Opus 4.5): a solo-agent harness produced a game that looked okay but wasn't playable; the full planner+generator+evaluator harness — with upfront "contract negotiation" defining done-ness per sprint — produced a functional game, at higher cost and time.
- Case study 3 (in-browser DAW on Opus 4.6): a simplified two-stage harness (planner expands a one-sentence prompt into a full spec; generator builds it in one continuous session relying on SDK context compaction; evaluator runs once at the end) finished in ~4 hours for about $125.
- Big takeaway: every harness component encodes an assumption the model can't do something on its own (context reset = assumption the model can't manage its own context); those assumptions go stale as models improve, so harness design has to keep evolving rather than being a one-shot setup.

## ✅ Action Items
- If your agent grades its own work, split it into a separate generator and evaluator agent instead — don't trust self-evaluation for anything subjective.
- Define explicit, weighted grading criteria for the evaluator (not "is this good?") so subjective quality becomes gradable, and weight the criteria toward where your model is known to be weak (e.g. avoiding generic "AI slop" patterns).
- Give the evaluator agent real tools to interact with the output (browser automation via Playwright MCP, or equivalent) instead of only reading source code or text.
- Treat every harness component (context resets, planner agents, contract negotiation) as an assumption about model limitations — revisit and simplify your harness as the underlying model improves, rather than assuming a fixed architecture is permanent.
